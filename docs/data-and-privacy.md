# Data and privacy

KubeNeuron sends no usage data, metrics or reports to its authors and does not check for updates. Data leaves your cluster only through the connections listed below: destinations you configure, the Kubernetes and cloud APIs the software needs to run, and image pulls from the publishers' registries.

## Agent privileges

The installed agent runs privileged and shares the host PID namespace, including in dry-run mode. It reads host kernel fault messages and uses host namespaces and tools for configured diagnostics and node actions. Dry-run controls remediation execution. It does not change the agent pod's permissions.

## What is stored

The incident audit records the node UID, observation time, and status and available transition time for five Kubernetes node conditions (Ready, MemoryPressure, DiskPressure, PIDPressure and NetworkUnavailable). These records are deleted with the incident.

For each incident KubeNeuron records the accelerator worker pods observed on the node (namespace, name, UID) and the training jobs that own them: kind, namespace, name, UID and status. It also records the observation time and the completion index when verified for an Indexed Job. It reads them with `get` on Jobs, JobSets, RayClusters and RayJobs that own the affected pods. It does not store or log job specifications, environment variables, commands or annotations. Job names stay in the incident record and audit trail; they are not added to metric labels and are left out of notifications by default. They are deleted with the incident.

For each incident KubeNeuron also records evidence read from the Kubernetes API about its node: the accelerator and high-performance network resources the node advertises and how many are allocatable, the state (running, not ready, missing) of the vendor's component pods on the node, and an estimate of where the fault is. When the same class opens on several nodes, it records the node names, the class and the incident IDs of the group. It does not record the names of those pods, of jobs or of users in the evidence, and none of it goes into notifications; the metric `kubeneuron_incident_evidence_total` carries only the class and the three states. The evidence is deleted with the incident.

For an incident opened from an [accelerator health profile](accelerator-health.md), KubeNeuron records the profile, the rule, the Node condition type, the condition's reason, and when the condition last changed. It does not read or store condition messages. This is deleted with the incident.

When the training report endpoint is enabled, a job can report three facts to the controller: a checkpoint (an opaque identifier and an optional step), a resume from a checkpoint, and progress (a step number). The controller accepts a report only from a pod that belongs to that job, identified by its Kubernetes service account token. It links the report to the job using the pod's namespace and verified owner UID. The namespace and owner name appear in incident details and in `kubeneuronctl report --json`. The controller stores the facts with the incident and deletes them with it. It timestamps them on receipt. It neither stores nor logs the token. Checkpoint identifiers are excluded from logs and metric labels. Checkpoint identifiers are limited to 128 characters and cannot be URLs or paths; do not put storage locations, credentials or personal data in them. The endpoint is off by default and reports stay inside the cluster.

Incidents, approvals, actions, operational state and the audit trail live in SQLite on a volume in your cluster by default. If you configure PostgreSQL, they live at the database address you supply. Approval and audit records identify the person who approved, rejected or triggered an action. Password sign-in accounts use a Kubernetes Secret. For automatic mode, the policy and audit trail record the identifier declared in `enabledBy`. KubeNeuron excludes that identifier from metric labels, logs and telemetry exports.

The managed metrics store keeps metrics in your cluster for 30 days by default. You can change its retention period. GPU series identify nodes and GPU UUIDs. The managed Collector drops standard workload labels for pod, namespace, container and pod UID before storage unless you enable `keepWorkloadLabels`. Additional labels you enable in dcgm-exporter are stored as sent.

Managed Grafana keeps its administrator account in your cluster. The installation generates its password in a Secret that is removed with the installation.

## Connections

- With the training report endpoint enabled, job pods send reports to the controller over HTTPS inside the cluster. The controller validates their tokens with the Kubernetes TokenReview API.
- The installer runs on your workstation. It downloads the install manifest from GitHub Releases and, with `--version latest`, asks the GitHub API for the newest release. Installed components do not check for updates.
- The agent sends observations to the configured controller. When a DCGM client is available it can contact the DCGM host engine. Host tools and scripts you supply may make their own connections.
- Cluster components access the Kubernetes API. The controller connects to the configured database, OIDC provider and notification destinations. Slack, PagerDuty and webhook recipients receive incident details. The web panel loads no third-party scripts, fonts or analytics. OIDC sign-in redirects the browser to your identity provider.
- With the AWS provider enabled, cloud operations use the EC2, EKS and Auto Scaling APIs. The AWS SDK may contact STS, instance metadata or container credential endpoints for authentication.
- With the Azure provider enabled, cloud operations use the Azure Resource Manager API for the AKS cluster and its node pools. The Azure SDK may contact Microsoft Entra ID and the instance metadata endpoint for authentication.
- With the GCP provider enabled, cloud operations use the Compute Engine and Kubernetes Engine APIs, and the Cloud Resource Manager API to check the controller's permissions. The Google SDK may contact the Security Token Service, the IAM Credentials API and the metadata server for authentication.
- When `spec.safety.acceleratorHealth.dra.enabled` is set, the controller lists the cluster's `resource.k8s.io/v1` ResourceSlices. Of each device it reads the driver, pool and device name, its `uuid` attribute and its taints; it keeps a taint's value only when it is a number or a documented value, and nothing else of the slice. An incident opened from this read records the device, its UUID and the taint; this is deleted with the incident. It writes nothing to the API server for this.
- When `spec.cloud.gcp.tpuInfraHealth.enabled` is set, the controller connects to `monitoring.googleapis.com` and lists the TPU health metric `compute.googleapis.com/instance/tpu/infra_health` in the projects of its TPU nodes. Of each series it reads the instance's zone and name, `health_status`, `unhealthy_category` and the times of the samples. It does not store or log `reservation_id`, `machine_id`, `block_id`, `cluster_id`, `subblock_id`, `machine_type` or the instance's other metadata and user labels, and it does not log the answer. An incident opened from this read records the source, the rule, the category and when the run of samples began; this is deleted with the incident. It writes nothing to Google Cloud for this.
- The controller reads interruption signals that the cloud or its node tooling puts on Node objects (taints, labels and conditions). A `cloud-interruption` incident records the kind, the deadline and the source of each notice, without the cloud's text. When `spec.cloud.aws.interruptionQueueURL` is set, the controller also connects to the regional Amazon SQS endpoint and reads that queue: from each event the source, detail type, event ID, time, instance ID and state, and for AWS Health events the event ARN, service, category, `startTime`, `statusCode` and affected instance IDs. The message body, the Health `eventDescription` and the event's account ID are not stored or logged. The controller deletes the messages it has read from that queue; it writes nothing else to AWS for this.
- On Azure the controller lists Events of the affected node in the `default` namespace and keeps only their source, reason and time.
- While a replacement runs, KubeNeuron writes a tag on the AKS node pool: `kubeneuron-replacing` with the machine name, or `kubeneuron-successor` with a token derived from the incident's operation identifier, each with the pool's node count. The tag is removed when the replacement finishes. It contains no workload or user names.
- A remove-first replacement on a fixed-size GKE node pool is recorded on the incident: the operation identifier, the instance, the node pool, its zonal instance groups and node count before, the phase, the GKE resize operation's name and the `gcloud` command that sets the size back. Nothing is written to Google Cloud to mark it. It is deleted with the incident.
- With managed monitoring, the OpenTelemetry Collector, VictoriaMetrics and vmalert exchange metrics inside the cluster, and vmalert sends metric alerts to the controller; the alerts carry node and GPU identifiers, not workload names. External telemetry destinations require your configuration. The audit log stays in the configured controller database.
- Managed Grafana queries the configured metrics store. By default, usage reporting, update checks, Gravatar and external snapshot sharing are disabled. The installation references the unmodified Grafana OSS image (AGPL-3.0) from its publisher.
- Your cluster pulls unmodified images from their publishers. The managed monitoring stack references OpenTelemetry Collector, open VictoriaMetrics and vmalert (Apache-2.0). It can scrape an existing dcgm-exporter. The NVIDIA driver and dcgm-exporter are used under their vendors' terms when present. The optional external dependency manifests have their own installation and licence information.

## Deletion and access

Uninstall retains the controller's state by default. See the [installation guide](install.md) for the explicit state deletion option. Manage an external PostgreSQL database or external metrics store through its own retention and deletion controls.

The operator never deletes the managed metrics volume. `deploy/install.sh --uninstall --delete-data` deletes it together with the controller's state; a plain uninstall keeps it, and it can still contain metrics and node names. To erase the volume, run `kubectl delete pvc <name>-metrics-store -n <namespace>`, substituting the KubeNeuron resource name and its configured namespace. Underlying disk disposal follows the volume's reclaim policy.

Your team controls access and retention. Handle user identities in approval and audit records according to the requirements that apply in your environment.
