# Security review — v0.8.0 workload-safe GPU recovery (source review, signed off)

Status: **complete against the v0.8.0 candidate source; signed off by
the maintainer (@andriipetruk) on 2026-11-07 with the release decision
(D0: GO), before the tag was created.** It reviews the diff this release makes to the controller, the
operator-generated RBAC, the store and the API, and the unit, kind and lint
checks that pin each claim below. It is a review of the code in this
repository, not a third-party audit. Its evidence is the unit tests, the
offline kind gate (`make test-integration-kind`), the examples fixture
(`make test-workload-safe-kind`) — all CPU-only — and one hardware run on a
single Tesla T4 (2026-11-05; the Limitations section says what it did and
did not cover). The v0.8.0 entry in `CHANGELOG.md` records the gates on the
candidate source; a second review pass (2026-11-05, an independent model
review of the candidate) found the defects listed under *Corrections after
review* and they are fixed on the candidate. Report anything that
contradicts this page through
[SECURITY.md](https://github.com/kubeneuron/kubeneuron/blob/main/SECURITY.md).

## Scope

v0.8 adds six things, all read-only or annotation-only, configured under
`spec.safety` and all defaulting to off: a fail-closed device topology
classifier (S1), a checkpoint *advisory* when an incident parks for approval
(S2), bounded gang coordination through `checkpoint-group` (S3), a durable
impact preview the approve can be bound to (S4), read-only workload context
resolvers for batch Jobs, Kueue and KubeRay (S5), and one shared eligibility
function (S6). The [design record](workload-safe-recovery-design.md) holds
the decisions; this page checks the boundary it promises:

> The release adds no remediation action, no device-scoped action on
> partitioned or shared GPUs, no write to Kueue, Ray or DRA objects, and no
> network path from the controller to any workload.

The previous reviews ([v0.5.0](security-review-v0.5.0.md),
[v0.6.0](security-review-v0.6.0.md), [v0.7.0](security-review-v0.7.0.md))
still describe every other authority-bearing surface, unchanged. The v0.6.0
review's arguments for Phase 1 — default off, namespace allowlist, the one
`pods: patch` grant and its in-code confinement, no veto, failure never
blocks — carry over to everything v0.8 builds on them, and are not repeated.

## 1. What authority the controller gains, and when

The controller's ClusterRole is generated by the operator from the compiled
policy, so the grants below exist only while the matching block is enabled
and vanish on the next reconcile after it is disabled
(`internal/operator/resources.go`, pinned by `internal/operator` tests that
compare the generated rules to the opt-ins):

| Opt-in | Grant | Verbs |
| --- | --- | --- |
| `checkpointCoordination.enabled` (v0.6, unchanged) | `pods` | `patch` beside the existing `get,list,watch` |
| `topologyClassifier.dra.enabled` (S1) | `resource.k8s.io/resourceslices` | `get,list,watch` |
| `impactPreview.workloadContext.batchJobs` (S5) | `batch/jobs` | `get,list,watch` |
| `impactPreview.workloadContext.kueue` (S5) | `kueue.x-k8s.io/{workloads,localqueues,clusterqueues}` | `get,list,watch` |
| `impactPreview.workloadContext.kuberay` (S5) | `ray.io/{rayclusters,rayjobs}` | `get,list,watch` |

Nothing else. In particular the advisory (S2), the groups (S3) and the
preview (S4) add **no verb**: the advisory and the peer request reuse the
Phase 1 `pods: patch`, the group listing and the preview reuse `pods: list`
the controller already holds, and the topology classifier reads node status
and labels the controller already watches. The static roles
(`config/rbac/operator_role.yaml`, the chart's `rbac.yaml`) gain the
read-only delegation rules the operator needs in order to grant the
resolvers' read access, and no write verb on any of those groups. A test
fails if a generated or static role carries `pods/exec`, `pods/attach`,
`pods/portforward` or `pods/ephemeralcontainers`, and the examples fixture
asserts at run time that the controller's ServiceAccount cannot `patch`
Kueue Workloads or RayClusters.

## 2. No network path to a workload

Every interaction with a workload is a write of annotations onto its own Pod
object through the API server, with the Phase 1 guarded JSON Patch (test on
`uid` and `nodeName`, closed key sets, workload-owned keys never touched).
The controller opens no connection to a Pod or Service, reads no URL off an
annotation and calls no webhook: the only HTTP clients in the controller
remain the ones to the notification channels the operator configured. The
new routes (`GET …/impact-preview`, `POST …/impact-preview/recompute`) are
operator-token routes on the existing listener; no port, listener or inbound
path is added.

The Ray example (`examples/checkpoint/kuberay-ray-train`) acknowledges by
patching its *own* Pod, because a Ray worker Pod does not exit when a
training function returns. That takes a namespaced Role the example creates
for the worker ServiceAccount (`pods: get,patch` in `ml-training`). It is
the workload's credential, held by the tenant, and the only credential in
the examples; KubeNeuron neither issues nor reads it. Platform teams that
copy the example should scope it as the example does.

## 3. The advisory promises nothing and cannot be extended

The advisory (S2) is a notice, not a request: it stamps
`kubeneuron.io/checkpoint-advisory{,-at,-incident,-round,-reason,-next-action}`
and no deadline key. A test pins that an advisory-only Pod carries no
`checkpoint-deadline-at`, so no reader can mistake it for a window, and the
kind gate asserts the same on real Pods. It runs under its own budget
(default 10s, ceiling 60s) at park time, after the park has been committed,
so a slow or failing advisory never delays the state change it follows.
When the round ends without its disruption (rejection, expiry, a step that
no longer disrupts) the notice is withdrawn best effort; the withdrawal
writes exactly one key (`checkpoint-advisory-withdrawn-at`) and the opt-in
stays untouched (asserted in kind). In `DryRun` nothing is patched and the
audit row says what would have been advised.

None of this changes `BoundedWait = clamp(request-or-default, maxWait,
budget)`: the advisory writes no key the wait reads, and the Phase 1 tables
that prove no annotation can lengthen a window beyond `min(maxWait, budget)`
now also cover a Pod carrying advisory keys and group keys.

## 4. Gangs are bounded and cannot veto

A `checkpoint-group` (S3) is a tenant-written DNS label on the Pod; an
invalid value makes the Pod `group-invalid` and it is treated as a single
workload. Peers are found by one paged Pod list per group, in the same
namespace only, with a hard page cap (4000) and the policy's `maxGroupSize`
(default 64, ceiling 512) above which the whole group is `group-too-large`
and no peer is asked; `crossNode` defaults to off, so by default a peer on
another node is never touched. A peer's deadline comes from the same formula
as the local candidates', capped by the step's budget, and a peer's silence
is an `expired` outcome, never a hold: the drain proceeds on the node it was
approved for and KubeNeuron does nothing on the peer's node — no eviction,
no cordon, no taint (the kind gate asserts the peer Pod and its node are
unchanged after the drain). The peer still receives a request, and an
adapter such as the bundled Ray example stops its training loop in
response, so "node-local" describes KubeNeuron's infrastructure actions,
not the application's whole reaction.

## 5. The preview is read-only, sealed and fails closed

The impact preview (S4) is computed from the listing the controller already
performs for the disruption and from the classifier's read-only evidence; it
writes nothing anywhere but its own store table. Its payload is bounded
(`maxItems` 10..1000, 256 KiB) and its computation by `budget` (at most
60s); past either it records `unavailable` with a reason rather than a
partial document presented as whole. It is sealed by a SHA-256 over its
canonical JSON, stored once per (incident, round, computed_at) with the
digest as the identity, and never recomputed in place: a recompute is a new
row behind the operational idempotency table.

`requireForApproval` is the only place the preview carries authority, and
that authority is a refusal. An approve must carry the digest of the current
round's newest preview; a missing or stale digest is 409
(`ErrImpactDigestRequired`, `ErrImpactDigestMismatch`), an unavailable
preview holds the approve until a recompute succeeds, and rejecting is never
held. The decision row and the incident detail carry the digest the human
saw, so an audit can show which counts a given approve was bound to. The
preview estimates nothing: it carries counts, groups, contexts and the
classifier's verdict, and the documentation lint
(`hack/stale-claims.txt`) forbids the public spellings of a saved or lost
training claim.

## 6. The classifier narrows and never acts

The topology classifier (S1) reads node status, GPU Feature Discovery labels
and, under its own opt-in, `resourceslices`; it writes nothing. Its only
output that touches authority is `device_actions`, and the only value a
policy can act on is the one it renders for a whole-device node; `mig`,
`time-sliced`, `dra-managed`, `mixed` and `unknown` all render `refused`,
and a conflicting or missing input is `unknown`. A narrowing test pins that
no input can raise the verdict above what the previous evidence allowed, and
the action registry's bijection test pins that no device-scoped action was
added for the refused topologies. A kind node without GPU evidence previews
as `unknown` / `refused`, which the examples fixture asserts as the expected
result, not an error.

## 7. Resolvers read, and prove they read

The three context resolvers (S5) are dynamic, unstructured clients that
`get`/`list` the owner Job, the Kueue Workload admitted for it, and the
RayCluster / RayJob labels, under the preview's own budget. Each is behind
its own opt-in; an absent CRD group, a forbidden read or a timeout becomes a
`not_observed` reason on the preview rather than a failure. No code path
calls `Update`, `Patch` or `Delete` on those groups; the generated RBAC
grants none of those verbs; and the examples fixture reads back the Kueue
Workload, RayJob and RayCluster objects after a full advisory → approve →
drain run and fails if any `managedFields` entry names a KubeNeuron manager.
The documentation lint forbids the public spellings of a Kueue, KubeRay or
Ray Train "integration" or "support"; the only legal shape before a pilot is
"read-only context from …, demonstrated in kind, not validated on a
production fleet".

## 8. Store, API and CLI

The store gains one table (`impact_previews`) and one column
(`approvals.impact_digest`) — SQLite 0024, PostgreSQL 0015 — and one
column (`operational_idempotency.result_digest`, SQLite 0025, PostgreSQL
0016), all exercised on both engines by the migration and conformance
tests; the upgrade notes carry the same "disable the policy before rolling
back" rule as v0.6. Migrations are forward-only: the release's
upgrade/rollback rehearsal proves that a v0.7.0 binary **refuses** the v0.8
schema and that the documented rollback is a restore of the pre-upgrade
snapshot, after which the rows written since the upgrade are gone
([upgrade notes](upgrade.md#v080-workload-safe-recovery-notes)). Prune
deletes previews with their incidents. The two new routes require the
operator token; the recompute route is an operational mutation behind
`Idempotency-Key`, and a replay answers with the preview its key produced.
`kubeneuronctl approve --round --impact-digest` binds the approve to the
digest the human read (the digest the notification shows); with `--round`
and no digest the CLI prints the preview and stops rather than binding to
whatever is current, so a human who approves from the CLI has the same
binding as one who approves from the panel and never approves a preview
recomputed behind their back.

## 9. Examples and fixtures are evidence about the protocol, not about frameworks

`examples/checkpoint/*` are CPU-only toys whose README each opens with the
sentence that they demonstrate the annotation protocol and are not evidence
that any framework integrates with KubeNeuron. `hack/kind-workload-safe.sh`
installs Kueue and the KubeRay operator from the archives pinned by URL and
SHA-256 in `deploy/kubernetes/dependencies/versions.lock.yaml`, and the Ray
image by tag and digest; its `--verify` mode runs the trainer and the
sidecar locally through an advisory and a request and proves its own
assertions fail on 28 deliberate defects, so a green cluster run is a
result of the assertions and not of their absence.

## Limitations

- **One Tesla T4.** The hardware the project can rent exercised exactly
  what it can: one opted-in Pod holding one GPU on one virtualized node
  (the advisory, the digest-bound approve, the request, the exit, a real
  drain), the classifier on that node as `whole-device` and, under the
  device plugin's `replicas: 2`, as `time-sliced`; the v0.8.0 CHANGELOG
  entry records the run (2026-11-05). Nothing here has run against a MIG
  partition, a DRA driver, a multi-node gang or a GPU that can be reset:
  on that node the agent's report is degraded (the hypervisor withholds the
  PCI reset), so every classification was `refused` with `ReportNotReady`
  and the `eligible` verdict is still CPU-only evidence. That first
  hardware read also found the classifier collapsing such a node to
  `unknown`; the correction (layout kept apart from readiness) narrows
  nothing in this review — a degraded report still refuses every device
  action — and adds no write, no grant and no network path.
- **Kubelet latency.** The Downward API file a workload reads refreshes on
  the kubelet's sync loop, not on the patch; very short advisory lead times
  may be consumed by it. One observation outside kind (3–4 s on EKS, G3
  2026-11-05); not a fleet figure.
- **Snapshot semantics.** The preview, the advisory and the group listing
  act on the Pods present when they ran; a Pod that appears afterwards is
  not described, not advised and not asked. This is the Phase 1 race,
  unchanged.
- **The tenant's own credential.** A workload that acknowledges by writing
  its state key needs `patch` on its own Pod; the Ray example shows one
  scoped way to grant it. KubeNeuron cannot make that grant safer than the
  namespace it lives in.
- **Sign-off.** Signed off by the maintainer (@andriipetruk) on 2026-11-07
  together with the release decision (D0: GO). The content was reviewed
  against the final candidate (`7c5801e`, the code the tag carries); the
  CHANGELOG reference above is what records the gates on that candidate.

## Corrections after review

A second review pass on 2026-11-05 (an independent model review of
`591982f`: code and logic, then product-line alignment) found defects
that bear on this page's claims. Each is fixed on the candidate with a
regression test; the CHANGELOG entry lists them all. The ones that touch
a security claim above:

- **§3, DryRun.** The advisory consulted only the incident's own `DryRun`
  stamp, so an installation switched to `DryRun` after an incident opened
  could still have that incident patch workloads. The advisory now reads
  the live gate the way step execution does; the sentence "nothing
  patched in `DryRun`" holds for the installation's mode, not only the
  incident's.
- **§3, withdrawal.** A withdrawal was recognised by the mere presence of
  a `withdrawn-at` key, so a later round's notice stamped over a withdrawn
  one read as withdrawn, and the withdrawal patch did not test the round
  it was about. A withdrawal now counts only when it is not older than
  the stamp, and the patch tests the advisory's incident and round.
- **§4, budget.** The audit row per group was written outside the
  coordination window; many stalled groups could spend the reserve the
  disruption owns. The rows are inside the window now.
- **§5, idempotency and ordering.** A recompute reserved its key before
  computing and answered a replay with the round's newest preview; the
  newest preview was chosen by text order. Both are fixed (compute,
  persist, then key with the result digest; newest by parsed time).
- **§8, the CLI.** `kubeneuronctl approve --round` bound the approve to
  whatever preview was current at approve time. It now requires the digest
  the human read, which the notification carries.
- **Resolvers.** The Kueue and batch Job readers could describe another
  owner's object; they attribute nothing by name alone now.
